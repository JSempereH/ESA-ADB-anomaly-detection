# RRCF and Drift-Aware Isolation-Forest Ensembles (IForestASD → EiForestASD → BWOAIF → ADDAEIL) for Multivariate, Contaminated, Online Anomaly Detection

## What is Robust Random Cut Forest (Guha et al., ICML 2016), how is it used in production, and is there recent (2024–2026) validating/extending work?

### Takeaway
RRCF (Guha, Mishra, Roy, Schrijvers, ICML 2016 / PMLR v48:2712–2721) is a streaming-capable ensemble of randomly-cut binary trees that scores anomalies via "collusive displacement" (CoDisp) — how much a point's removal would shrink the model complexity (tree depth/bit-depth) of the rest of the data. It underlies AWS's production RCF offerings (SageMaker RCF, Kinesis Data Analytics `RANDOM_CUT_FOREST`), but recent (2024) head-to-head benchmarking by the Online Isolation Forest authors found RRCF ~40× slower than a modern incremental alternative with no AUC advantage, which is the single most decision-relevant fact for this project.

### Cited Findings
- The original paper: Guha, S., Mishra, N., Roy, G., Schrijvers, O. "Robust Random Cut Forest Based Anomaly Detection on Streams." ICML 2016, PMLR 48:2712–2721. It defines anomalies without assuming a parametric distribution, based on how much a new point changes the rest of the data (model complexity), and the summary structure can be updated incrementally as points arrive. — [PMLR](https://proceedings.mlr.press/v48/guha16.html), [Amazon Science](https://amazon.science/publications/robust-random-cut-forest-based-anomaly-detection-on-streams)
- Production use — **SageMaker RCF**: unsupervised algorithm attaching an anomaly score per data point; low=normal, high=anomaly; common practice flags points >3 standard deviations from the mean score; trains on `application/x-recordio-protobuf` or `text/csv`; scales well across feature count, dataset size, and instance count. — [AWS SageMaker docs](https://docs.aws.amazon.com/sagemaker/latest/dg/randomcutforest.html)
- Production use — **Kinesis Data Analytics `RANDOM_CUT_FOREST`**: a SQL function that scores a streaming record as anomalous if distant from other records; only numeric columns are scored; the model is built live from the current stream (no use of older runs/history beyond a `timeDecay` parameter); docs explicitly warn that casting a business problem into this function "requires domain expertise" including column selection and normalization. — [AWS Kinesis SQL reference](https://docs.aws.amazon.com/kinesisanalytics/latest/sqlref/sqlrf-random-cut-forest.html)
- **Recent (2025) spacecraft-adjacent application of (plain, not robust) RCF**: an AWS ML blog (June 2025) applies SageMaker RCF to NASA/Blue Origin BODDL-TP lunar descent/landing data — 10-dimensional vectors (3 position + 3 velocity + 4 quaternion). Config used: `feature_dim=10`, `num_samples_per_tree=512`, `num_trees=100`, `threshold_percentile=0.9`, batch scoring (`batch_size=1000`) on an `ml.m5.4xlarge` instance — **not actually run as a streaming/online job**, despite being framed as a streaming use case; real-time deployment is listed only as future work. The 0.9 threshold is not explained/calibrated against any ground truth (data is unlabeled); the post only qualitatively claims RCF handles sensor noise "fairly well." — [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/using-amazon-sagemaker-ai-random-cut-forest-for-nasas-blue-origin-spacecraft-sensor-data/)
- A 2025 IEEE conference paper applies RRCF to real-time anomaly detection on precision electrical instruments (multimeters, nanovoltmeters) — a recent but non-spacecraft streaming-measurement validation, reporting improved accuracy/precision/recall vs. unspecified comparators. — [search result summary, HIT scholar record](https://scholar.hit.edu.cn/en/publications/real-time-anomaly-detection-of-precision-instruments-based-on-rob/)
- **No RRCF-specific extension or validation on spacecraft/satellite multivariate telemetry from 2024–2026 was found.** A 2026 ESA-ADB benchmark paper and a 2026 Brno thesis on satellite telemetry anomaly detection do not appear to use RRCF (not confirmed with full text access). — [search results, this researcher's queries]
- **Direct, quantitative 2024 comparison against RRCF** (see next question's table) comes from the Online Isolation Forest paper (Leveni et al., ICML 2024), which used RRCF as a baseline via the PySAD implementation with τ=32 trees and a window of 256. — [Online Isolation Forest, ICML 2024 full text](https://object.cloud.sdsc.edu/v1/AUTH_da4962d3368042ac8337e2dfdd3e7bf3/ml-papers-txt/ICML/2024/online_isolation_forest__390f9caf.txt)

### Inferences
- RRCF's production deployments (AWS) are mature and well-documented, but the most recent *applied* spacecraft-telemetry case study (2025, Blue Origin/NASA) uses plain RCF in **batch** mode, not a genuine online walk-forward protocol, and does not solve or even address the zero-label threshold-calibration problem central to this project — it simply hand-picks a 0.9 percentile threshold.
- There is no evidence of an active 2024–2026 research program extending or re-validating RRCF itself; the method appears to have settled into "production baseline" status rather than an active research frontier, while attention has shifted to incremental/histogram-based successors (Online Isolation Forest).

### Gaps
- No access to the full IEEE precision-instruments paper (only abstract-level summary available) to check if it discusses contamination-robustness or online deletion semantics.
- No confirmation of whether the 2026 ESA-ADB benchmark paper or satellite-telemetry theses include RRCF as a baseline (full text was not accessible to verify).

## Is there a usable, maintained Python package supporting genuine online/streaming insertion and deletion of points?

### Takeaway
Yes — the `rrcf` PyPI package (kLabUM/rrcf, cited via its JOSS paper) exposes `insert_point()` and `forget_point()` on its `RCTree` class, which is genuine incremental tree surgery (not batch rebuild), and its own documented streaming example uses a FIFO sliding window exactly matching a walk-forward online protocol. However, "maintained" is questionable — it is a small, single-paper-driven research package, not an actively developed library, and it offers no built-in contamination-robust thresholding.

### Cited Findings
- `rrcf: Implementation of the Robust Random Cut Forest algorithm for anomaly detection on streams`, Bartos, Mullapudi, Troutman, *Journal of Open Source Software* 4(35), 2019 — describes itself as the first open-source implementation of the algorithm, reproducing the original paper's sine-wave anomaly onset/offset experiment. — [JOSS paper](https://joss.theoj.org/papers/10.21105/joss.01336.pdf)
- Installation: `pip install rrcf`; Python 3 only; core dependency numpy ≥1.15; pandas/scipy/scikit-learn/matplotlib only needed for doc examples — i.e., very light dependency footprint, good fit for a laptop-CPU setup. — [kLabUM/rrcf GitHub](https://github.com/kLabUM/rrcf)
- API: `RCTree.insert_point(x, index=...)` and `RCTree.forget_point(index)` are genuine incremental operations on the tree structure; the documented streaming usage pattern creates empty trees, feeds a `rrcf.shingle`-based sliding window, and for each new point inserts it into every tree in the forest while evicting the oldest point (FIFO) once a size limit is reached — this is an authentic online/windowed protocol, not retraining from scratch. — [kLabUM/rrcf GitHub](https://github.com/kLabUM/rrcf)
- Anomaly score: `tree.codisp(index)` returns "collusive displacement" (CoDisp) — in the README's toy example an inlier scores 1.75 vs. an outlier at 39.0; `codisp_with_cut_dimension(leaf)` additionally returns which feature/dimension drove the cut, giving a built-in feature-attribution mechanism potentially useful for per-channel explainability (relevant to the project's 47-channel multivariate setting). — [kLabUM/rrcf GitHub](https://github.com/kLabUM/rrcf)
- Inputs are n×d arrays (explicitly multivariate); README claims good performance on high-dimensional data with reduced influence of irrelevant dimensions, and documents a multivariate feature-importance workflow. — [kLabUM/rrcf GitHub](https://github.com/kLabUM/rrcf)
- A separate package `rcf3` on PyPI is a **Rust** implementation with Python bindings offering a broader feature set (feature attribution, forecasting, an `mStream` detector for mixed numeric/categorical streams) — a different codebase from the original algorithm's reference Python port; could be a faster alternative if `rrcf`'s pure-Python performance proves too slow (see complexity findings below). — [rcf3 PyPI/docs](https://docs.rs/crate/rcf3/0.5.1)
- PySAD (a streaming-AD library) also ships an `IForestASD`/RRCF-style wrapper used as the baseline in the Online Isolation Forest ICML 2024 benchmark (τ=32 trees, window=256), confirming a second, benchmark-grade Python entry point for RRCF beyond the standalone `rrcf` package. — [Online Isolation Forest full text](https://object.cloud.sdsc.edu/v1/AUTH_da4962d3368042ac8337e2dfdd3e7bf3/ml-papers-txt/ICML/2024/online_isolation_forest__390f9caf.txt)

### Inferences
- `rrcf`'s pure-Python, pure-numpy implementation with no vectorized batch tree operations likely explains its very poor wall-clock performance observed in the ICML 2024 benchmark (next section) — tree insert/forget in pure Python per point, per tree, is inherently slow at scale. This is a real laptop-CPU feasibility risk for 47 channels at 18s resolution over long walk-forward horizons.
- Given the light dependency footprint and genuine streaming API, a small-scale pilot (handful of channels, short walk-forward window) is cheap to attempt, but scaling to the full 47-channel, multi-month walk-forward protocol should be assumed slow based on the quantitative evidence in the next section.

### Gaps
- No independent benchmark of `rrcf` package's raw throughput (points/sec) was found outside the PySAD-wrapped comparison; it's unclear how much of the ICML 2024 RRCF slowness is attributable to the PySAD wrapper vs. the core algorithm/package.
- "Maintained" status (recent commit activity, open issues) of kLabUM/rrcf was not directly checked (GitHub activity/last-commit date not verified in this research pass).

## How does RRCF differ from standard Isolation Forest and from this project's Online Isolation Forest (Leveni et al., ICML 2024)? Is a distinct implementation worth it?

### Takeaway
Conceptually, RRCF differs from IForest/Online-IForest by scoring anomalies via **collusive displacement** (model-complexity change upon point removal, i.e., a "deletion-based" notion of anomalousness) using **randomly-cut trees with explicit insert/forget tree-surgery operations**, rather than Online-IForest's histogram-based, bin-splitting multi-resolution approach. Empirically, a direct 2024 benchmark found RRCF statistically equivalent to Online-IForest in detection accuracy (AUC) but **roughly 40× slower**, and worse than IForestASD on AUC on the same suite — so implementing RRCF as a second, genuinely distinct method is very likely **not worth the engineering time** for this project: it offers no accuracy edge over the already-implemented Online Isolation Forest, at drastically higher runtime cost.

### Cited Findings
- From the ICML 2024 Online Isolation Forest paper's own characterization: RRCF is "the first attempt to adapt Isolation Forest to streaming data... dynamically manages tree structures, and introduces a novel anomaly score based on the discrepancy in tree complexity when a data point is removed from the stream," and the paper explicitly states "tree modifications performed by RRCF tend to be resource-intensive" compared with Online-IForest's bin splitting/aggregation. — [Online Isolation Forest full text (ICML 2024)](https://object.cloud.sdsc.edu/v1/AUTH_da4962d3368042ac8337e2dfdd3e7bf3/ml-papers-txt/ICML/2024/online_isolation_forest__390f9caf.txt)
- **Quantitative benchmark (Table 4 of the paper, median over 30 runs, 11 stationary datasets)** — O-IFOR = Online Isolation Forest, asd-IFOR = IForestASD:

  | Dataset | O-IFOR AUC | asd-IFOR AUC | RRCF AUC | O-IFOR time(s) | asd-IFOR time(s) | RRCF time(s) |

- On the single non-stationary (drifting) dataset tested (INSECTS, 33-dim wing-beat features, 5 real drift points from temperature changes), the paper states only that "all the tested algorithms are affected in a similar way by sudden changes" and that execution times were not influenced by distribution changes, with O-IFOR remaining fastest — no RRCF-specific AUC/time numbers are given for this drifting case in the extracted text. — [Online Isolation Forest full text (ICML 2024)](https://object.cloud.sdsc.edu/v1/AUTH_da4962d3368042ac8337e2dfdd3e7bf3/ml-papers-txt/ICML/2024/online_isolation_forest__390f9caf.txt)
- Complexity: Online-IForest average-case time is stated as O(n·τ·log₂(ω/η)) with space O(τ·√(ω/η) + ω) independent of stream length n (τ = number of trees, ω/η relate to window/bin-resolution parameters). The paper gives **no asymptotic complexity for RRCF**, only the qualitative "resource-intensive" characterization. — [Online Isolation Forest full text (ICML 2024)](https://object.cloud.sdsc.edu/v1/AUTH_da4962d3368042ac8337e2dfdd3e7bf3/ml-papers-txt/ICML/2024/online_isolation_forest__390f9caf.txt)
- None of the 11 stationary benchmark datasets, nor INSECTS, is multivariate industrial/sensor/spacecraft telemetry — they are general outlier-detection benchmark sets (fraud, network intrusion (HTTP/SMTP), forest cover, donations, taxi time series, etc.) plus one biological sensor stream (insect wing-beat frequency).

### Inferences
- Given this project already has a validated, genuinely incremental Online Isolation Forest implementation, and the one head-to-head academic comparison available shows RRCF is **no better on accuracy and ~40× slower**, implementing RRCF as an additional distinct method offers very poor expected return on implementation time for a "next few hours" scope. The conceptual distinction (deletion-based CoDisp vs. histogram bin-splitting) is real, but it does not translate into an empirical edge in the one comparison found.
- If runtime were not a constraint, RRCF's per-dimension CoDisp attribution (`codisp_with_cut_dimension`) could be a nice-to-have for channel-level explainability that Online-IForest may not natively offer — but this is a minor interpretability feature, not a detection-quality argument.

### Gaps
- No comparison data was found specifically pitting RRCF against Online Isolation Forest on a genuinely contaminated, multivariate, high-frequency industrial/spacecraft telemetry stream (the INSECTS set is the closest proxy in the one paper found, and it lacks RRCF-specific numbers).
- The `rrcf` package's own documented complexity/throughput was not independently verified outside of the PySAD-wrapped ICML 2024 numbers, so it's possible a leaner integration (bypassing PySAD overhead) performs meaningfully better than the 1274s/dataset figures above — but no evidence either way was found.

## ADDAEIL (Li, Nair, Wang, 2025) and predecessors (IForestASD, EiForestASD, BWOAIF): exact drift-detection and tree-swap mechanisms

### Takeaway
Across the whole lineage, the drift mechanism is always "statistical test over a sliding window triggers replacement of some subset of isolation trees," but the sophistication increases from IForestASD (whole-ensemble rebuild) → EiForestASD/BWOAIF (selective tree removal) → ADDAEIL (dual-test drift *intensity* score controlling a continuous replacement *ratio*, plus a per-tree ranking test to choose *which* trees to replace). ADDAEIL's mechanism is now described in enough detail to reimplement: (1) a drift-intensity score from combined KS + Mann-Whitney U tests on the base vs. current window maps to a bounded replacement ratio (capped at 60%), and (2) within that budget, trees are ranked and replaced in ascending order of per-tree Mann-Whitney U p-value (comparing each tree's path-length distribution on base vs. current window) — the most-affected trees are swapped first, new trees trained fresh on the current window.

### Cited Findings
- **IForestASD** (Ding & Fei 2013, as implemented/extended by a 2021 MDPI *Computers* paper, "Anomalies Detection Using Isolation in Concept-Drifting Data Streams," Computers 2021, 10(1), 13, an extended ICCSA 2020 paper): built IForestASD on scikit-multiflow/River; drift handling added via **ADWIN** (adaptive sliding window change detector) and **KSWIN** (Kolmogorov–Smirnov windowing), with KSWIN extended by the authors to handle n-dimensional streams; three ADWIN/KSWIN-based extensions were proposed and found to use fewer resources than baseline IForestASD with similar-or-better detection (F1, execution time, memory). — [MDPI Computers 2021, 10(1),13](https://0-www-mdpi-com.brum.beds.ac.uk/2073-431X/10/1/13)
- PySAD's `IForestASD` implementation explicitly does **not** implement concept drift handling itself ("concept drift is not implemented since it is a part of the simulation") — it is a plain sliding-window IForest; drift-awareness is only in the research extensions above, not in this commonly-used library version. — [PySAD docs](https://pysad.readthedocs.io/en/stable/generated/pysad.models.IForestASD.html)
- **EiForestASD** (JECEI journal, exact mechanism from search-level summary — full PDF not deeply parsed): keeps the isolation forest as the live detector; drift handling is **window-based**, and — critically — it discards **only** the isolation trees that no longer fit the new concept (rather than rebuilding the whole ensemble as plain IForestASD does), then reconstructs just those trees. Evaluated on 6 real-world + 2 synthetic streams; reports 19% lower computation time and 9% higher anomaly detection rate vs. baseline IForestASD. Implemented in Python/Scikit-Multiflow. — [JECEI article](https://jecei.sru.ac.ir/article_2228.html)
- **BWOAIF — "Bilateral-Weighted Online Adaptive Isolation Forest"** (NOT black-widow-optimization; Hannák, Horváth, Kádár, Szalai, *Statistical Analysis and Data Mining*, 2023, DOI 10.1002/sam.11612, Nokia Bell Labs): unsupervised IForest-based streaming detector; adapts by **removing old trees and creating new ones**; authors claim gradual adaptation to slow drift and fast adaptation to sudden shifts; tested against slow/fast concept shift, concept split, concept appearance, and concept disappearance scenarios; claimed to have "only a few, easily human-interpretable hyperparameters." The exact bilateral weighting formula and the precise tree-discard trigger/threshold were **not accessible** in available search results (only abstract-level detail). — [Nokia Bell Labs publication page](https://nokia.com/bell-labs/publications-and-media/publications/bilateral-weighted-online-adaptive-isolation-forest-for-anomaly-detection-in-streaming-data), [Statistics Views summary](https://www.statisticsviews.com/article/open-access-from-statistical-analysis-and-data-mining-bilateral-weighted-online-adaptive-isolation-forest-for-anomaly-detection-in-streaming-data/)
- **ADDAEIL** (Li, Nair, Wang, *Algorithms* (MDPI) 18(6):359, June 2025, DOI 10.3390/a18060359) — full algorithmic detail retrieved:
  - **Module 1 (distribution-based drift intensity):** Kolmogorov–Smirnov (KS) and Mann–Whitney U (MWU) tests compare a fixed "base" window against the current sliding window; their results are averaged (equal weighting) into a drift score in [0,1]; this score is linearly mapped to a bounded **replacement ratio**, with the upper bound explicitly capped so that **no more than 60% of base detectors are replaced in one update** (lower bound value not recoverable from the extracted text).
  - **Module 2 (structure-based tree selection):** For each base IForest tree individually, an MWU test compares that tree's **path-length distribution** on the base window vs. the current window, producing a per-tree two-sided p-value; trees are **ranked by ascending p-value** (most drift-affected = smallest p-value = replaced first); no extra model training needed for this ranking step.
  - **Combination:** Module 1's replacement ratio sets *how many* trees get replaced out of the ensemble (size N, tested with N≈50–100 in sensitivity analysis); Module 2's ranking decides *which* trees. Replaced trees are freshly trained on the current window; the rest are kept (incremental, not full rebuild).
  - **Datasets:** Yahoo A3 (synthetic, simulated anomalies + incremental drift), NAB — Numenta Anomaly Benchmark (50 real + synthetic series, labeled, sudden + incremental drift), and CEMACS (real-world ocean surface temperature readings every 30 min over 2 years). **None are industrial, spacecraft, or network-traffic telemetry**; NAB is framed partly around IT/server monitoring use cases.
  - **Baselines compared:** ECOD, LODA, MemStream, LSTM-VAE, STAD, AEADF — notably **none of IForestASD, EiForestASD, BWOAIF, RRCF, or Online Isolation Forest** are used as baselines; ablation only compares against a static (non-drift-aware) IForest and ADDAEIL's own variants. This means **no published apples-to-apples comparison exists** between ADDAEIL and its own named lineage (IForestASD/EiForestASD/BWOAIF) or against RRCF/Online-IForest.
  - **Runtime (measured on an NVIDIA Jetson Orin NX 16GB, on CEMACS):** training time 0.117s, per-window latency 0.15–0.21s, max memory 340MB, model size 0.24MB. No asymptotic complexity given.
  - **Code availability:** none provided; the paper's data-availability statement says data will be released "upon publication," no code repository is linked.
  — [ADDAEIL, Algorithms (MDPI) 18(6):359, 2025, full text extracted via reader proxy](https://www.mdpi.com/1999-4893/18/6/359)

### Inferences
- The ADDAEIL mechanism (dual statistical test → bounded replacement ratio → per-tree ranked swap) is specified precisely enough to reimplement from scratch on top of the project's existing IsolationForest-based code: it needs (a) a maintained "base window" buffer and "current window" buffer of raw feature vectors, (b) KS + MWU tests on some per-window summary statistic (likely per-feature or on a global distance/score distribution — the exact statistic compared by KS/MWU in Module 1 was not recoverable, a genuine ambiguity for implementation), (c) per-tree path-length distributions already computable from a scikit-learn-style IsolationForest's `decision_path`/`apply`, and (d) straightforward ranking/replacement logic. This is a from-scratch implementation task (no code exists anywhere in the lineage), estimated as a non-trivial afternoon-to-day task, not a quick drop-in.
- Given ADDAEIL has never been benchmarked against RRCF or Online Isolation Forest (which the project already has), and its own validation datasets are NAB/Yahoo/ocean-temperature (not multivariate contaminated industrial telemetry), there is **no existing evidence this family would outperform the project's already-validated LOE/USDR/CRTF/Kalman models** on ESA-ADB-style data. The MDPI Algorithms journal is a legitimate but lower-tier/high-throughput venue; claims of "consistently outperforms state-of-the-art" should be read with appropriate skepticism absent independent replication.
- Module 1's ambiguity (what exactly is distribution-tested — raw features? anomaly scores? which features for 47-channel multivariate data?) is a real open design question if implementing ADDAEIL for this project's 47-channel setting; the paper's own experiments all appear to be univariate or low-dimensional (ocean temperature, NAB series), not a 47-dimensional telemetry vector, so the published recipe does not directly specify multivariate extension.

### Gaps
- The lower bound of ADDAEIL's replacement-ratio mapping, the exact drift-score thresholds, and whether Module 1's KS/MWU test operates per-feature (and how results are aggregated across 47 channels) vs. on a single aggregate statistic were not recoverable from the accessible text (reader-proxy extraction was incomplete/summarized, not the verbatim paper).
- BWOAIF's exact "bilateral weighting" formula and tree-discard trigger condition were not found beyond abstract-level description; the full DOI-linked paper (10.1002/sam.11612) would need direct access (likely paywalled) to extract implementable detail.
- No validation of IForestASD/EiForestASD/BWOAIF/ADDAEIL family on any real spacecraft, satellite, or general industrial-sensor multivariate dataset was found; closest are ocean temperature (ADDAEIL/CEMACS) and insect wing-beat frequency (used only in the separate Online-IForest paper, not this family). This is a genuine, confirmed gap in the literature, not a search failure — multiple distinct searches converged on the same non-industrial benchmark sets (NAB, Yahoo, INSECTS, standard outlier-detection UCI-style sets).

## Has the IForestASD/EiForestASD/BWOAIF/ADDAEIL family been validated on real industrial/sensor/spacecraft telemetry? Is there existing Python code, or is from-scratch implementation required?

### Takeaway
No member of this family has been validated on real spacecraft or general multivariate industrial-sensor telemetry in any source found — validation datasets across the whole lineage are generic streaming-ML benchmarks (synthetic/network-traffic/financial-fraud sets for IForestASD's base evaluation context, NAB/Yahoo/ocean-temperature for ADDAEIL, unspecified real/synthetic streams for EiForestASD, synthetic drift-scenario data for BWOAIF). No usable Python code exists for EiForestASD, BWOAIF, or ADDAEIL anywhere found (including GitHub); only plain, non-drift-aware IForestASD exists in a library (PySAD), meaning any of the drift-aware variants would require a full from-scratch implementation.

### Cited Findings
- PySAD ships `IForestASD` but explicitly without drift detection ("not implemented since it is a part of the simulation"). — [PySAD docs](https://pysad.readthedocs.io/en/stable/generated/pysad.models.IForestASD.html)
- A targeted GitHub/code search for "EiForestASD" and "BWOAIF" returned no matching repositories; the closest unrelated hits were an "iforest-variants" ablation-study repo (Extended Isolation Forest variants, unrelated to EiForestASD despite the similar name) and a plain Go isolation-forest port. — [search results, this researcher's query]
- ADDAEIL's own paper confirms no code repository is provided (data availability statement only, no code link). — [ADDAEIL full text](https://www.mdpi.com/1999-4893/18/6/359)
- EiForestASD's own reference implementation (per its abstract-level summary) uses Python + Scikit-Multiflow, but no public repository link was found in search results. — [JECEI article](https://jecei.sru.ac.ir/article_2228.html)
- The 2021 MDPI *Computers* IForestASD-with-ADWIN/KSWIN paper built its work on River/scikit-multiflow, an open-source streaming-ML framework that itself only natively offers Half-Space Trees for streaming anomaly detection (not IForestASD) — suggesting even this earliest, most-cited variant required custom implementation work by its own authors rather than reusing a maintained library. — [MDPI Computers 2021, 10(1),13](https://0-www-mdpi-com.brum.beds.ac.uk/2073-431X/10/1/13)

### Inferences
- Any implementation of this family for the project would be **entirely from-scratch**, built on top of the project's own IsolationForest-based code (as the task description anticipates), since there is no maintained package for any drift-aware variant — only the non-drift-aware base IForestASD exists in PySAD, and even that would need the drift logic bolted on manually.
- Given (a) no real industrial/spacecraft validation anywhere in this lineage, (b) no code to build from, (c) ADDAEIL's own ambiguous multivariate extension, and (d) the Online Isolation Forest 2024 benchmark showing a close relative (IForestASD) winning on AUC but still far slower than the project's already-implemented Online Isolation Forest — the risk-adjusted value of implementing ADDAEIL (or any ancestor) from scratch in a few hours is low to moderate at best: moderate because the drift-ranking idea (Module 2: per-tree path-length MWU test) is genuinely novel relative to what's implemented and could be grafted onto the existing Online Isolation Forest or PyOD IForest cheaply as an ablation; low because there's no evidence it would beat the current best performer (Kalman local-trend model) or the already-implemented LOE/USDR/CRTF family, and building Module 1's multivariate drift-intensity scoring correctly is the hard, underspecified part.

### Gaps
- No full-text access to BWOAIF or EiForestASD primary sources to confirm implementation feasibility details (window sizes, tree counts, exact statistical thresholds) at the same depth as achieved for ADDAEIL.
- Could not verify current GitHub repository activity/maintenance status beyond the absence of search hits — a private or very recently published repo could exist without yet being indexed.
